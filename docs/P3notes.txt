>> SPSC improves the producer-consumer pipeline substantially over the mutex queue.
>> False sharing has a massive measurable cost 
>> Batching improves single-thread throughput by amortizing per-message overhead.

>> SPSC improved the handoff mechanism
|__>> Pipeline is still dominated by queue residence time under the unpaced producer workload.
|__>> faster handoff helps but does not remove backlog under an unpaced producer.

>> Producer spins show the producer frequently tried to push when the ring buffer was full. The consumer did not need to wait for data.
|__>> Producer is faster than consumer/pipeline drain rate.
|__>> Queue fills.
|__>> Producer spins waiting for space.
|__>> Consumer remains busy draining.

>> Even when two threads update logically independent counters, they can interfere badly if the counters share the same cache line. 
|__>> ~4.85x throughput improvement when counters were separated onto different cache lines. (false sharing benchmark)
|__>> Cache line layout can dominate performance even when threads are not logically sharing the same variable.

>> Batching improved amortized processing cost per message
|__>> Benchmark does not yet measure batch formation delay.
|__>> Batch size 32 was best for my setup.

| Benchmark               |         Throughput |                             Key latency result | Main takeaway                                            |
| ----------------------- | ------------------ | ---------------------------------------------- | -------------------------------------------------------- |
| Single-thread baseline  |   **3.43 M msg/s** |            Book p50 **229 ns**, p99 **769 ns** | Fastest pure local update baseline                       |
| Mutex producer-consumer |   **0.80 M msg/s** | Pipeline p50 **82.36 ms**, book p50 **390 ns** | Queue wait dominates                                     |
| SPSC producer-consumer  |   **2.10 M msg/s** | Pipeline p50 **31.04 ms**, book p50 **304 ns** | Much better than mutex queue, still queue wait dominated |
| False sharing unpadded  |  **93.83 M inc/s** |                                            N/A | Severe cache line contention                             |
| False sharing padded    | **454.72 M inc/s** |                                            N/A | ~4.85x faster by avoiding false sharing                  |
| Batching size 1         |   **3.40 M msg/s** |                 p50 **230 ns**, p99 **733 ns** | Baseline batch mode                                      |
| Batching size 8         |   **4.18 M msg/s** |                 p50 **211 ns**, p99 **475 ns** | Strong improvement                                       |
| Batching size 32        |   **4.33 M msg/s** |                 p50 **205 ns**, p99 **459 ns** | Best throughput here                                     |
| Batching size 64        |   **4.28 M msg/s** |                 p50 **212 ns**, p99 **471 ns** | Slight regression vs 32                                  |


->The book update path remains fast, but the mutex-based producer-consumer pipeline introduces significant queueing delay under an unpaced stress workload.
